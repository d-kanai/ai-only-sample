# 日次セキュリティレビューは Opus で、変更ファイルを 1 つずつ読ませ、読んでいないファイルを出す

- 日付: 2026-10-03
- 状態: 採用
- 関連: Issue #435 / `.github/workflows/security-review.yml` / workflow/20261002-daily-security-review-in-actions.md

## 背景
workflow/20261002-daily-security-review-in-actions.md の日次セキュリティレビューを、Secret の登録後に手動で初めて動かした（run 37155145661、2026-10-03）。初回なので 24 時間前の main からの 49 コミット・202 ファイル・約 1.1 万行が対象で、Sonnet 5.5 が 8 turn・約 20 秒で「指摘なし」を返した。どこまで読んだかはログから分からない（action は Claude の出力を出さない設定）。この量を 8 turn で読み切ったとは考えにくい（推測）。前の ADR の見直す条件の「見落としが目立つ（Opus に上げる）」に当たる。

## 決定
- モデルを Opus 5.5（`claude-opus-5-5`）にする。`--max-turns` は 150、job の `timeout-minutes` は 45 分にする。
- プロンプトで、変更ファイルを一覧してから 1 つずつ差分を読み、外から入る値を扱う変更は呼び出し元と行き先まで追うよう求める。
- 結果の JSON に、読んだファイルの一覧（`reviewed_files`）を必須で足す。ワークフローは変更ファイル（docs/work-logs/ と画像を除く）と比べ、読んでいないファイルを warning とジョブのサマリに出す。失敗にはしない。
- それ以外（実行の時刻・範囲・認証・権限・advisory の下書き）は前の ADR のまま。

## 理由
- daiki の判断（2026-10-03、スレッドの判断カードで「深くする」）。浅いレビューの「指摘なし」が続くと、安心の根拠を誤る。
- 2 回目からは前回の成功した実行以降の差分だけなので、普段の 1 回の量は初回より小さく、消費の増え方は限られる見込み（未確認）。
- `reviewed_files` は Claude の自己申告なので読んだ証明にはならないが、読んでいないと申告したファイルは機械的に見える。
- 失敗にしない: 起点は成功した実行だけから取るので、失敗にすると同じ範囲を毎回見直し続け、Claude が毎回同じファイルを飛ばすと抜け出せない。

## 採用しなかった案
- Sonnet のままプロンプトだけ強める: 初回の浅さがモデルの読み方か、プロンプトかを切り分けられておらず、daiki は両方を選んだ。
- PR（ファイル）ごとに Claude を分けて呼ぶ: ワークフローが複雑になり、呼び出しの回数だけ起動の消費が増える。今の形で読んでいないファイルが多ければ見直す。
- 読んでいないファイルがあればジョブを失敗にする: 上の理由。

## 影響
- 良い点: 1 回のレビューが深くなり、どこまで読んだかがジョブのサマリで分かる。
- 悪い点: 1 回の消費と所要時間が増える（Opus での実際の値は未確認。次の実行で確かめて timeout を直す）。
- 見直す条件: 読んでいないファイルが毎回多い、所要時間が 45 分に近い、または消費が目立つとき。
