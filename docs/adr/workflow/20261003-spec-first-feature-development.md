# ドメイン機能の開発は 4 種の .feature に仕様を書き、整合性を確かめてから TDD で実装する

- 日付: 2026-10-03
- 状態: 採用
- 関連: Issue #443 / `.claude/rules/workflow/feature-dev.md` / `.claude/rules/quality/testing.md`

## 背景
仕様は E2E（`apps/e2e/spec`）・API ジャーニー（`spec/journey`）・API 仕様（`spec/api`）・domain 仕様（`spec/domain`）の 4 種の .feature に分かれている。同じ機能の依頼を複数回計画させた評価（2026-10-03 の work-logs、ルールの再現性の評価）で、境界値・エラーの扱い・テストの置き方が回ごとに揺れた。daiki は AI の書いたコードを読まず、.feature の項目で仕様を確かめたい。

## 決定
- ドメイン機能の開発では、最初の step で 4 種の .feature に仕様を整理して書く。
- 4 種の仕様の整合性（食い違い・抜け）を確かめ、問題が無ければ .feature を満たす実装を TDD で進める。
- どのテストから着手するかは AI が判断する。整合性の確認の後に daiki の確認を挟むことは決めない（daiki の依頼の文面どおり、AI の判断で進める）。
- 規則は常時読み込む `.claude/rules/workflow/feature-dev.md` に置く。

## 理由
- daiki の依頼（2026-10-03）「E2E feature、ジャーニー feature、API feature、domain feature にまず仕様を整理して書くところを最初の step にする。全ての仕様の整合性を判断して大丈夫なら Test 駆動で進める。どのテストから対応するかは AI が良いものを判断して良い」。
- 仕様を先に固定すると、実装の揺れは .feature の範囲に閉じ、daiki は .feature だけで変更を確かめられる。
- 層ごとに仕様を書いてから並べると、層の間の食い違い（例: domain の上限と API の検証の上限）を実装の前に見つけられる。
- 開発の進め方なので、`paths` で読む rules ではなく常時読み込む workflow/ に置く（機能の開発はどのファイルを触る前にも始まる）。

## 採用しなかった案
- スキル `feature-dev` にする（評価の改善案 1）: 呼ばれないと読まれず、最初の step が飛ばされうる。
- 整合性の確認の後に daiki の承認を必須にする: daiki の依頼に無く、待ちで作業が止まる。

## 影響
- 良い点: 実装の前に仕様がそろい、PR で .feature を読めば変更が分かる。
- 悪い点: 小さな変更でも 4 種を見る手間がかかる（変更の無い種類は書かず、理由を PR に書く）。
- 機械化: 未対応。「実装より先に .feature を書いたか」はコミットの順でしか見えず、決定的に検査しにくい。
- 見直す条件: 仕様の揺れが続くとき、または daiki の確認を挟みたくなったとき。
